# Nautra PoC — 開発規約（基本設計書 13.2 の PoC 適用版）

このアプリは `projects/docs/` の要件定義書・基本設計書 Ver1.2 を正本とする PoC。

スコープ: **要件定義書の全業務領域（9本）を実装済み**。
船内画面 V-01〜V-10（打刻・履歴・本日の集計・船内承認・航海日誌・点検/保守・
作業/待機/燃料/引継・シフト/配置表・同期状態・相談/アンケート）＋ 安全・事故報告・お知らせ、
陸上画面 S-01〜S-18（後述「陸上アプリ」節）。
デザインは `design/poc_design/` のデザインキャンバスが正本（後述の「デザイン」節）。

**要件との対応を見失わないこと**: 画面・判定を足すときは、要件定義書の該当節番号を
コメントに書く。逆に節番号の無い機能は、なぜ要るのかを説明できるようにする。

## コマンド

- `npm run dev` — 開発サーバ（http://localhost:3100）。オンデマンドコンパイルのため遅い
- `npm run preview` — 本番ビルドで起動。**デモ・体感確認はこちら**
- `npm run stop` — 3100 を掴んでいるサーバを止める（`scripts/free-port.mjs`）。
  `dev` / `start` は起動前に自動でこれを行うので、`EADDRINUSE` で落ちることはない
- `npm run test` — Vitest（ドメイン・同期のテーブル駆動テスト）
- `npm run typecheck` — tsc --noEmit
- `npm run build` — 本番ビルド

## ガードレール（違反コードを書かない・見つけたら直す）

1. `(vessel)` 配下で Server Components のデータ取得禁止（オフライン破壊防止）
2. 一次記録（timeRecords / records / サーバ events）への UPDATE/DELETE 禁止。訂正は差戻し→
   `supersedesId` 付き新規レコード（航海日誌・シフト計画も同じ規則。`latestBySupersedes`）
3. 法令閾値（14h/72h/休息10h 等）・安全基準（アルコール 0.15mg/L）をドメイン関数や画面内の
   定数として持つこと禁止。`src/rules/` から引数注入し、判定結果に適用版を記録する
4. 導出値（年齢・配乗可否・集計値）を入力カラムとして保持しない
5. HeroUI の直接 import は `src/ui/` 配下のみ。画面は `@/ui`（自前の部品）と
   `@/ui/heroui`（HeroUI の部品）経由で使用。**この2本を1つにまとめない**——
   1つの入口に 40 以上を並べると、`StatusChip` を1つ取るだけの画面にも HeroUI 一式が
   束ねられ、陸上のどの画面でも 690KB を落とすことになる（実測で First Load JS 482KB → 170KB）
6. 製品名は `src/i18n/ja.ts` の `PRODUCT_NAME` からのみ参照（ハードコード禁止）
7. `(vessel)` ⇔ `(shore)` の相互 import 禁止（共有は src/domain・src/ui 等経由）
8. 同期イベントは冪等キー必須。未知種別は破棄せず隔離（quarantine）し、**アプリ更新後の
   同期で再処理**する（`reprocessLocalQuarantine`。旧版の端末が先に受信した配信が欠けたまま
   にならないようにする）。**判別ユニオンはレジストリから生成**しているので手で足す必要はない
9. **新しい記録種別の追加はスキーマを定義して `SYNC_ENTITY_REGISTRY` に登録するだけ**で
   完了させる（船内記録は `records.ts`、マスタ・事務は `masters.ts`）。種別ごとに
   Push/Pull・Dexie テーブル・適用処理を個別実装しない（汎用 `records` テーブル + `appendRecord`）
10. シフト・配乗計画・マスタは陸上正本（船内は参照のみ）。船内の実績は打刻等の別レコードで
    保持し、計画を実績で上書きしない。**例外: 当直シフトは船長だけ船内でも作成・変更できる**（レビュー SHIFT-04・
    利用者の判断）。レジストリの `shift_plan` は `origin: "both"` + `vesselAuthorRole: "captain"` で、サーバは
    **記録した時点の**船員マスタで記録者が船長かを確かめ、違えば隔離する（`checkVesselAuthorPolicy`。マスタが後から
    届いたら見直して受理に戻す）。陸上と船長が同じ当直を別々に変えたら双方を残し「⚡競合（要確認）」と示す。
    船内で陸上に受け付けられなかった当直は端末だけで有効にしない（`serverQuarantinedIds`）。PoC は Push に船員の
    認証が無いので記録者は自己申告（本番は認証済みセッションと突き合わせる）
11. **`<p>` の中に `div` を描く部品を置かない**。ブラウザが `<p>` を勝手に閉じるため、
    ハイドレーションが必ず壊れる（React error #418）。HeroUI の `Chip` / `Card` が該当する。
    `StatusChip` は `<span>` に作り直したので文中に置ける。混在させたい行は
    `<div className="flex …">` にする。検出は `e2e/scan-nesting.mjs`
12. **`"use server"` のファイルから非 async の値を export しない**（定数・型・初期状態も含む）。
    Next.js が Server Action として扱おうとして実行時に 500 になる。定数はクライアント側に置く
13. **要配慮個人情報（既往歴・服薬）を参照したら監査ログを残す**（10.3 / 12.6）。
    `writeAuditLog({ action: "view_sensitive", … })`。ログに値そのものを載せない
14. **マスタの更新経路は1画面だけ**（12.3）。船員マスタは `/shore/crew/[id]/edit` のみが更新し、
    一覧・カルテ・届出からは書き換えない。**船舶マスタは `/shore/fleet/new` と `/shore/fleet/[id]/edit` だけ**
    （レビュー VESSEL-02。配乗計画などは「＋ 船を登録」で案内するだけ。`server/vessel-master-service.ts`）

## デザイン（`design/poc_design/Nautra デザイン.dc.html` が正本）

暖かいグレーの紙面に白いカードを並べた、**密度の高い実務ツール**。丸みと影で柔らかくせず、
**枠線と明度差だけで面を切る**。1画面に情報を詰めて、めくらずに突き合わせられるようにする。

> 正本は `design/poc_design/` のデザインキャンバス（`.dc.html`）。画面の対応表は同フォルダの
> `github.md`。`projects/docs/DESIGN.md` は前の版（モノクローム）で、**いまは参照しない**。

  `text-foreground-500` / `text-danger` / `bg-default-100` / `bg-primary` などの意味クラスは
  **すべてここ経由**なので、トークンを変えれば全画面に効く。
- 材質クラス: `src/app/globals.css`（`.ui-card` / `.ui-row` / `.ui-inset` / `.ui-bar` /
  `.ui-sidebar` / `.ui-dark` / `.ui-modal` / `.ui-table` / `.ui-btn-*` / `.ui-field`）。
  **画面は独自の影・角丸・背景色を作らない**（基本設計書 6.3）。
- 面の部品: `src/ui/`（`SurfaceCard` / `SurfaceRow` / `StatBlock` / `Section` / `Eyebrow` /
  `DataTable` / `StepBar` / `StatusChip` / `CrewPhoto` / `SearchField` / `ConfirmDialog` /

### 角丸はほぼ立てる

**3px（小）/ 4px（カード）**。モーダルだけ 6px、顔写真の枠だけ 12〜14px、アバターは 50%。
丸みで柔らかくしない。

### 文字

**Noto Sans JP**（本文・見出し）と **IBM Plex Mono**（数値・時刻・ID・符牒）。
`@fontsource/*` がフォント実体を同梱するため、ビルド時も実行時も外部へ通信しない。
時刻・時間・件数は等幅＋`tabular-nums` で桁を揃える（船の記録は数字を読み比べるため）。

| クラス | 役割 | 大きさ |
|---|---|---|
| `text-2xs` | 符牒・群見出し（mono・字間 0.14em） | 10 |
| `text-xs` | 補助・チップ | 11 |
| `text-sm` | 副次本文 | 12 |
| `text-base` | 本文 | 13 |
| `text-lg` | 強めの本文・ボタン | 14 |
| `text-xl` | 小見出し | 16 |
| `text-2xl` | 画面名 | 17 |
| `text-3xl` | 人名・大見出し | 22 |
| `text-4xl` / `text-5xl` | 数値の主役 | 30 / 34 |

**船内アプリは同じ階層を1段上げる**（`.vessel .text-sm` = 13px / `.text-base` = 15px）。
要件定義書 10.2「船員の約半数が50歳以上。大きな文字」への対応で、デザインの刻みの中で
上げているため型の階層は崩れない。

### 色（ここが唯一の判断が要る所）

有彩色は **ブロンズ**（アクセント）と **レンガ**（警告）の2系統だけ。

- **例外: 船内ヘッダの通信状態だけ**は緑 `--online`（#2e7d4f）/ 赤 `--offline`（#b3261e）の
  塗りに白字で出す（レビュー SHIP-01。発注者の指定）。`navigator.onLine` と擬似オフラインの
  どちらかが切れていればオフライン。ほかの場所にこの2色を使わない

- **主操作・現在地・符牒 → `#917351`**（濃い側 `#6F5638`、暗い面の上は `#99877D`）
- **注意(caution) → `#EFE9E1` の下地に `#6F5638`**（要件定義書 3.2.5 の「上限接近」）
- **警告(violation) → `#F2E2DF` の下地に `#9B2A1E`**（同「超過」・破壊的操作）
- **適合(ok) → 無彩色**（`#E8E8E8` / `#333333`）。色が付くのは「見なければならないとき」だけ

派生する決まり:

- **0 件のときは色を付けない**（「期限が過ぎた 0」を赤で出さない）。`StatBlock` が構造で守る。
- **速報（`notice.level === "urgent"`）はブロンズ**にする。レンガは法令違反のために空けておく。
- **色だけに依存しない**。記号（✓ / ⚠ / ✕ / –）と文言を必ず併記する
  （色覚特性・直射日光下・白黒印刷でも読めるように）。
- 副次テキストは `text-foreground-500`（`#666666`）。**`#999999` より淡い文字を作らない**。

### ボタン

**見た目は役割で1種類に決める**。同じ役割のボタンを画面ごとに塗り/枠線で描き分けない。

- 主操作: `color="primary"`（HeroUI）または `.ui-btn-primary`（ブロンズの塗り）
- 副操作: `variant="bordered"` または `.ui-btn-ghost`（白地にヘアライン）
- 行内の小さな操作・絞り込み: `.ui-btn-quiet`、選択中は `.ui-btn-selected`
- 破壊的操作: `color="danger"` または `.ui-btn-danger`
- 記録の入口（船内で記録を始めるタイル）: すべて `RecordTile`（同じ高さ）

### レイアウト

- **陸上は 252px の暗いサイドバー**（`#231F20`）＋ **64px の白いヘッダ**。
  サイドバーは「全体 / 人員 / 手続き / 船・運航 / 管理」の5群（デザインの `NAV`）。
  群の見出しは mono 10px・字間 0.14em。現在地は**ブロンズの塗り** + `aria-current`。
  狭い画面ではヘッダ下の横並びに畳む。
- **船内 ⇄ 陸上はどちらからでも行き来できる**（`AppSwitchLink`）。船内はヘッダの右端、
  陸上はサイドバー下部と、サイドバーを畳む幅では横メニューの右端に置く。本番は別の機械なので
  業務の操作と混ざらない位置に置く（デザイン正本の `goShore` / `goVessel`）。
- **ヘッダは画面名を出す唯一の場所**。画面側に `<h1>` を置かない
  （`_components/screen-meta.ts` が経路 → 画面名・戻り先を引く）。
  画面名の横の「一言」と、右肩の受信件数・競合件数・ルール版の札は**出さない**
  （レビュー 0-1 / LABOR-01。利用者には意味が通じない。同期の状態は S-01 と V-09 で見る）。
- **画面に説明文・番号付きの見出し・ルール版を置かない**（レビュー 0-1 / 0-2）。
  「◯◯できます」「◯◯は追記で残ります」のような文で伝えず、画面の作り（タブ・ボタンの名前・
  記号）で伝える。船内の `GroupHeader` は見出しを読み上げ用（`sr-only`）にだけ残す。
- **船内はヘッダ + 横タブ**（V-01〜V-12）。共用端末は横幅を記録に使うのでサイドバーを置かない。
  現在地は下辺 3px のブロンズ線。承認タブは船長にだけ出す。
  V-01 の進行中・V-04 の承認まちは**暗い帯**で、離れて立っていても読める大きさにする。
- **注意・警告の札（`StatusChip`）はマウスを載せると理由が出る**（レビュー LABOR-05 / 0-6）。理由が分かる所では
  `hint` に `describeCheck(c)` などの文を渡す。渡さなくても注意・警告には既定の説明が出る。札はリンクの中にも
  置かれるのでフォーカスは持たせず、読み上げには札の中の sr-only の文で届ける。
- 労務の集計期間はカレンダー（`labor/_components/labor-calendar.tsx`）で選ぶ（LABOR-03）。日ごとの判定を記号で
  並べ、押すとタイムチャートのその日へ。
- **陸上で外した当直（S-18 のゴミ箱）は船内でも出さない**。外した判定は `src/lib/trash.ts` の `trashedIdsOf` 1つで、陸上（`trashedEntityIds`）と船内（`useShiftPlans`）が共用する。
  **最新の版を選んでから外したものを除く**（`latestExcludingTrashed`。陸上で当直を読むところは `trash-service` の `currentShiftPlans()` を通す。
  船員一覧の「本日の当直」・週の当直・書き出しが、外した当直を出し続けていた）。逆の順にすると、変更してから外した当直の元の版が生き返る（船内に 22:00–23:00 が何本も残っていた）
- 区画は `Section`、表は `DataTable`（固定見出し + 最大高さでスクロール）、手順のある画面は
  `StepBar`（カードの上辺に横一列）を使う。**主題が多い画面はタブで分ける**
  （1画面1主題。S-15 は `?tab=` で切り替え、1枚が 3000px を超えないようにする）。
- 顔写真は `CrewPhoto` で置く。**常に同じ大きさの枠**で、写真が無いときは頭文字と `PHOTO` の
  印を出す（空欄にすると「壊れている」と読まれる）。寸法は `size` で選ぶ
  （一覧 lg 96×120 / **カルテ・船員の編集 2xl 192×240**（レビュー CHART-04 / CREWEDIT-05）/ 印刷 xl 124×156 / ボード sm 60×74 / タスク xs 44×54）。
  実データは**船員マスタとは別の `crew_photo` エンティティ**（端末で 248×310 まで縮めた
  data URL）。マスタに載せると住所を直しただけで画像ぶんの版が積み上がるため分けてある。
  登録は選んだ時点で保存され、マスタの保存ボタンとは別経路（`saveCrewPhotoAction`）。
- **書き出しは各画面の「◯◯を書き出す」から**（レビュー EXPORT-01〜03。専用画面は持たない）。
  入口は `(shore)/shore/_components/export-action.tsx`（権限 `manage_documents` が無ければボタンごと出さない）、
  問いかけは `export-button.tsx`（形式 → 列 → 中身 → ファイル名 → 保存先）。形式は **Excel（.xlsx・既定）/
  カンマ区切り（.csv）/ タブ区切り（.txt）**で、画面に「CSV」という言葉は出さない（拡張子だけ見せる）。
  保存先は File System Access API の「名前を付けて保存」（Chrome / Edge）、無いブラウザは通常のダウンロード。
  API は `/api/v1/shore/export`（`preview=1` で列と先頭5行。本体は監査ログに残す）。xlsx は
  `server/xlsx.ts` が無圧縮 zip で自前生成する（依存を増やさない）。対象の行は `server/export-service.ts` の
  `EXPORT_SETS`（船員/配乗/労務/シフト/作業/船舶/手続き/待機・荷役）。
- 絞り込みの入力は `SearchField`（左に ⌕、右に ✕）。1タップで消せるようにする。
- **船内の記録画面は「記録する ／ 過去を見る」を別の面に分ける**（レビュー 0-4。日誌・点検・作業記録・安全）。
  **同じ大きさのタブで並べない**: 塗られた「＋ 日誌を記録する」が記録を始めるボタンに見え、押しても入力が開かなかった
  （利用者の指摘 2026-10-14）。記録を始めるのは札（`RecordTile`。輪郭と右の「＋」の印 `RecordMark`）だけにし、
  過去へは右上の「☰ 過去の◯◯を見る」、戻りは「‹ 記録に戻る」（`RecordModeSwitch`）。押せる機器の札にも同じ印を付ける。
  部品は `_components/record-mode.tsx`（`RecordModeSwitch` / `PastFilterBar` / `usePastList`）。過去の一覧は
  **期間とキーワード**で絞る（0-5）。判定は `src/lib/record-filter.ts` の `filterPast` 1つだけ（空白区切りは AND、
  全角半角・大小を区別しない、開始/終了は逆でもよい）。絞った後に 30 件ずつ「もっと見る」。
- 船内承認（V-04）は「承認待ち」「承認済み」の2群。承認するとその日の札は承認済みへ移る。差戻した日は承認待ちに残る。
- **一覧を全件出さない**。既定は直近ぶんだけにし、「もっと見る」で広げる（V-02 の1日の打刻は新しい12件。古くても出すのは**まだ直していない差戻し**と**直近に直した3件**だけ。直した順は直した版の ULID で決める）。
  長さは `e2e/measure.mjs` で測れる。
- **取り返しのつかない操作は問いかけを挟む**。削除・無効化は `DeleteDialog`
  （扱いの選択 + 影響の一覧 + 確認のチェック）、差戻しは `RemandDialog`
  （よくある理由を並べ、理由なしでは送れない）。どちらも実体は消さず追記で表し、
  S-18 から30日以内に戻せる。

### 画面づくりの原則（レビュー ADMIN-03 の調査で取り入れたもの）

新しい UI フレームワークは足さない（HeroUI と自前の `@/ui` で足りる。依存を増やすと初期表示が重くなる）。
代わりに、よく知られた考え方を**この PoC の部品に対応づけて**使う。

| 考え方（出典） | この PoC での形 |
|---|---|
| 最小限の表示・再認より再生（Nielsen の10ヒューリスティクス #8 / #6） | 説明の文を置かず、札（`StatusChip` の `hint`）と見出しの `title` に移す。画面に出すのは名前・数・状態の記号 |
| 段階的開示（Progressive disclosure） | 主題はタブ（`?tab=`）、入力は「＋ ◯◯する」で開く（協定・手配・記録）。一覧の詳細は右側に1件だけ（安全・事故） |
| 1画面1つのこと（GOV.UK Design System "One thing per page"） | 作成中の届出は「次へ: ◯◯」の1手だけ。書類を作るは種別を1つ選んでその入力だけ |
| 選択肢の数を減らす（ヒックの法則） | 選ぶ前に絞る（行の中の「提出を記録」「直す」「手配する」は対象が決まった状態で開く） |
| 押す場所を近く・大きく（フィッツの法則） | 操作は対象の行・カードの中に置く（相談への回答・提出の記録）。下の別フォームで選び直させない |

**点検の道具**: `node e2e/text-audit.mjs`（陸上の全画面とタブを開き、句点を含む40字超の段落＝説明の文を数える。
`--max=0` で1件でもあれば終了コード 1）。入力されたデータは `data-user-text` を付けると数えない。

### やらないこと

- ブロンズ系・レンガ以外の有彩色を持ち込まない
- カードに影を付けない（縁はヘアラインで決める。影はモーダルだけ）
- 3px / 4px 以外の角丸を作らない（モーダル 6px・顔写真 12〜14px・アバター 50% を除く）
- グラデーション・色の付いた影・ぼかし（`backdrop-filter`）を使わない
- 本文を 11px 未満、または `#999999` より淡くしない
- 画面ごとに `<h1>` で画面名を繰り返さない（ヘッダと二重になる）

## PoC の簡略化（本番との差分）

- DB: Supabase PostgreSQL → JSON ファイル（`.data/store.json`）＋ IndexedDB
  - デモデータ版（`SEED_VERSION`）が上がるとストアを作り直す（旧ファイルは退避）。デモの時刻は `atHour(日, 時)` で作る
    （`at9(...).replace("T09", …)` は日本時間では効かず、全部9時になっていた）。
    船内端末は Pull 応答の `storeId` 変化を検知してレプリカを取り直す。旧レプリカは削除せず
    `replicaArchive` に退避し、未送信 outbox は保持する（一次記録を失わない）
- 競合ポリシーの適用: レジストリの `origin=shore`（船員マスタ等）を船内端末から Push した場合は
  サーバで隔離（`checkOriginPolicy`）。シフト計画は船長だけ船内から可（`checkVesselAuthorPolicy`）。supersedes の分岐は `findSupersedeConflicts` で双方保持のまま
  「競合（要確認）」として V-09 / S-01 に件数表示（自動解決しない）
- 端末側の未知種別は `quarantine` テーブルへローカル隔離（破棄しない）。同期クライアントの
  IndexedDB 単体テスト・fast-check プロパティテストは未実装（要 fake-indexeddb 導入）
- 配信範囲: レジストリの `distribution: "shore_only"`（陸上ユーザー）は船内へ配らない
  （`isVesselDistributable`）。**カーソルは絞り込みの前に決める**ので、配らない種別が
  末尾に並んでも端末が同じ範囲を取り直さない
- 認証: 船内は PIN、陸上はメール + パスワード。
  **権限判定の経路は本番と同じ**（`domain/authz/`）だが、RLS・テナント分離・MFA は未実装
  （デモ用固定テナント）。PIN はデモ値を平文で持つ。IC カード認証は本番で追加する
  - 陸上アカウントは追記型の `shore_user` エンティティ（`server/shore-user-service.ts`）。
    **招待するとアカウントの実体ができ**、本人が招待コードで登録するとサインインできる。
    ロール変更・無効化・パスワード再設定も同じエンティティの新しい版として積む。
    自分で決めたパスワードは **scrypt の派生鍵とソルトだけ**を持つ（平文は保持しない）。
    デモ用の種（`server/shore-staff-seed.ts`）だけは合言葉を平文で持ち、サインイン画面に出す。
  - **メールは送らない**。招待コードは S-15 の一覧に、再設定コードはサインイン画面に出して
    手渡しする（送信経路だけが未接続で、アカウントの作成・有効化は本物）
- 書き出しの Excel（.xlsx）は自前の最小構成（1シート・inlineStr・見出し太字・枠固定）。数式・書式・複数シートは扱わない
- 帳票は **HTML の印刷ビュー**（`@media print`）で、ブラウザ印刷から PDF 化する想定。
  本番は Cloud Run Jobs でサーバ生成し、電子保管する。Excel マクロ様式の取込は
  **CSV 経由**（外部ライブラリを増やさないため。xlsx 直読みは本番で対応）
  - CSV の文字コードは **UTF-8（BOM 付き）/ Shift_JIS(CP932) / UTF-8** から選べる
    （`server/csv-response.ts`）。CP932 の符号化表は Node の `TextDecoder("shift_jis")` を
    逆引きして実行時に組む（依存を増やさないため）。変換できない文字は `?` にし、
    件数を応答ヘッダと監査ログに残す
- 外部連携は未接続。AIS/GPS はストアから読む**アダプタ**（`position-service.ts` の
  `fetchPositions()`）に閉じてあり、商用 API はここを差し替えるだけで載る。
  電子届出（登録届出）・e-Gov も同様に生成物までを用意し、送信経路は未接続
- 給与は打刻から時間外を算出するが、**確定時の値を保存する**（後から再計算されては困るため。
  導出値を持たない原則の意図的な例外で、その旨をコードに明記してある）
- チェックリストテンプレートは定数（本番はテナント定義・版管理テーブル）
- 同期クライアントの IndexedDB 単体テスト・fast-check プロパティテストは未実装
  （要 fake-indexeddb 導入）
- 通知のプッシュ配信（Web Push）は未実装。船内は SSE + 定期同期で受け取る

## 認証とロール（船内アプリ）

- 船内はサインイン必須。共用端末のため「船員を顔写真リストから選択 + PIN」方式とし、
  セッションは端末内（IndexedDB meta）にのみ保持する（基本設計書 11.3。通信断でも成立）。
  実装は `src/lib/vessel-session.ts` と `/vessel/login`、ガードは `(vessel)/vessel/layout.tsx`。
- 権限判定は `src/domain/authz/roles.ts` の表が唯一の情報源。画面に条件分岐を散らさず、
  `usePermission()` / `PermissionGate`（`_components/permission-gate.tsx`）経由で使う。
  **書けない人には記録の入口を出さない**（レビュー 0-9・利用者の指摘）。「🔒 参照のみ」の案内（旧 `ReadOnlyNote`）は置かない。
  航海日誌は書けない人（甲板部員・機関長）には記録の札も「過去の日誌を見る」の切り替えも出さず過去の日誌だけ。点検・保守は出港前点検などを全員が書けるのでタブは残し、
  機器の保守を書けない人には機器の札を押せない「機器の状態」として見せる。
- ロールと主な差分（基本設計書 11.2 の権限マトリクスを船内画面に展開）:
  - 船長 captain: 全機能 + 日次労務の承認・差戻し + 対象船員の切替（他船員の参照）
  - 航海士 deck_officer: 航海日誌の記入。保守記録は参照のみ
  - 機関長 chief_engineer: 日常点検・保守の記入。航海日誌は参照のみ
  - 甲板部員 deck_rating: 打刻・点検・作業記録。日誌/保守は参照のみ、承認は不可
- 記録の作成者（recordedBy / crewMemberId）はサインイン中の本人。対象船員の切替は船長のみで、
  他ロールは常に本人固定（`useActiveCrew()`）。
- **PIN は船員ごとに異なり、4桁目の入力で自動照合する**（誤入力は PIN を消して入れ直し）。
  **指紋は扱わない**。**顔認証は本番で iPad のカメラによる照合（顔認証だけでサインイン）にする予定**で、
  いまはサインイン画面に「顔認証を使う（任意）」の欄を**デザインとして置いているだけ**（船員を選ぶと出る）。
  照合の仕組みが無いまま通すと他人として入れてしまうので、押しても PIN は飛ばさない。
  放置すると自動サインアウトし、
  サインイン画面に理由（⏱）を出す（共用端末で前の人の記録が見えないようにするため）。
- PoC の簡略化: PIN はデモ値をマスタに平文で保持し、ログイン画面に表示している。本番は
  Supabase Auth（+ 管理者ロールは MFA）と端末登録（sync_devices）を併用し、PIN はハッシュ化する。
- 画面の切り替えは**ヘッダ直下の横タブ**（`_components/vessel-tabs.tsx`）。メニュー画面を
  経由しないので、起動直後の1タップで打刻に入れる。`/vessel` はお知らせのホーム（速報とお知らせだけ）。

## 打刻の仕様（01 労働時間・打刻）

- **打刻できるのはサインイン中の本人のみ**（共用端末でも記録者を取り違えない。11.3）。
  対象船員の切替は打刻には効かない（船長も自分名義でしか打刻できない）。
- **打刻できる6種別（航海当直・荷役・スタンバイ・保守整備・その他作業・休息）を常に同じ大きさで**
  出す（デザイン正本の `PUNCH_CATS`）。折りたたむと臨時の作業ほど手数が増え、揺れる船上では
  打刻漏れの原因になる。タイルには**労働時間に入るかどうか**を書く（押したあとに気付くのでは遅い）。
  割り当てられた当直（`src/lib/assigned-work.ts` の `assignedWorkFor`。対応表 `SHIFT_TO_WORK` は
  打刻画面とシフト画面で共用）は札で示す。計画との差異は 04 の計画/実績対比で確認する。
- **休息（`rest`）は労働時間に数えない**。打刻できる種別には入れてあるが、
  `domain/labor-law/types.ts` の `countsAsWork` が false を返し、判定にも内訳にも入らない
  （休息時間は従来どおり「労働していない時間」から導く。二重に数えない）。
- 操作は**2段階**（作業タイルを押す → 確認の問いかけで「はい」）。押し間違いを一度で
  確定させない（6.3）。緊急作業・安全臨時労働の別枠（3.2.5⑥）はこの確認の中で選ぶ。
- **並列打刻**に対応する。`buildIntervals` は作業種別ごとに開始/終了を対応づけ、
  複数の進行中区間を返す。したがって**労働時間の合計は区間の和集合**（`mergeRanges`）で
  求める（同時刻を二重に数えない）。種別別の内訳は重複を含むため合計を超えうる。
- **履歴・事後入力・差戻し再入力は V-02（`/vessel/history`）に分けた**。「いま打刻する」のと
  「その日の記録を確かめる」のは目的が違い、同じ画面に載せると打刻ボタンまでが遠くなるため。
  事後入力は**理由が必須**で、履歴に「事後入力」と残る。
  時刻は秒まで表示する（`fmtTimeSec` / `fmtDateTimeSec` / `fmtElapsedClock`）。
- **割り当てられた作業（陸上・船長の作業指示 `work_task`）は打刻画面の上にカードで並べる**（レビュー PUNCH-05）。本人の未完了の分だけ
  （`useMyTasks`）。押すと同じ確認の問いかけで打刻し、打刻のメモに「作業: 題名」を残す。始めると作業は「着手中」、終えるときに
  「この作業を完了にする」を選ぶと「完了」になる（`advanceWorkTask`。追記で陸上のボードに届く）。作業種別は題名から推定
  （`workCategoryForTask`。当てはまらなければ「その他作業」）。
- 本日の集計（V-03）は作業ごとの帯の下に**合計の帯**を置き、同時に進めた分は「⧉ 同時に進めた時間」の札で示す（WORK-05。説明の文は置かない）。
- 進行中のまま 12 時間を超えた作業には終了打刻忘れの注意を出す（並列打刻では開きっぱなしが
  溜まりやすく、進行中区間は現在時刻まで労働として集計されるため過大計上になる）。
- 権限: `punch`（本人の打刻）/ `punch_after_entry`（本人の事後入力・差戻し再入力）は全ロール、
  `adjust_crew_punch`（他船員の打刻を参照し差戻しで調整）は船長のみ。直接修正は誰もできない。

## 労務管理記録簿の仕様（02）

- 表示は役割で分ける（11.2）。一般の船員は**自分の記録だけ**、船長（view_all_crew）のみ
  表示船員の切替と乗組員一覧が出る。他船員の記録を読むコードは船長向けコンポーネントに閉じる
  （本番では API の権限ガードと RLS でサーバから返さない）。
- 承認・差戻しは船長のみ（approve_labor）。**承認者はサインイン中の本人**を記録する
  （固定の船長 ID を使わない）。承認者は打刻を直接修正できず、差戻しで本人に再入力させる。
- 権限のないサブ画面はタブごと出さない（GroupHeader の tabs に permission を付ける）。
  権限外の画面には他船員の氏名も出さない（見出しに承認者名を書かない）。
- 判定の言い換えは `src/lib/labor-plain.ts` に集約する（画面に文言ロジックを散らさない）。
  法令用語ではなく「働いた時間 / 休んだ時間 / 休みが分かれた回数」等の日常語＋
  「あと◯◯働けます」「◯◯不足する見込みです」の一文で示す。判定自体は domain が行う。

## 航海日誌の仕様（03）／点検の統合先（05）

- **03 は航海日誌だけ**にした。点検は 05「船内保守・作業記録」へ移設し、機器の日常点検・保守と
  同じ画面（`/vessel/maintenance` = 「点検・保守」）にまとめる（レビュー: 内容が重なるため統合）。
  - `/vessel/checklist` は転送のみのルートとして残す（既存リンク・ブックマーク対策）。
  - 点検表の入力・項目追加は `_components/checklist-section.tsx` に切り出し、置き場所を変えても
    同じ振る舞いになるようにした。履歴は点検表の結果と機器の保守記録を**1つの並び**で見せる。
  - 操練・アルコール検知は `/vessel/safety`（05 の3つ目のタブ）。点検でも保守でもない安全記録として
    独立させ、1画面1目的を保つ。
- **記録項目は配信で決まる**。点検表・航海日誌の追加項目は `record_template`（追記型・
  `origin: "both"`）として上司（船長）と陸上の双方から配信する。項目の追加は
  「項目を1つ足した新しい版」を `supersedesId` 付きで配信し、旧版は保持する
  （過去の記録は記録時点の `templateVersion` を持つため意味が変わらない）。
  - 解決は `src/lib/record-templates.ts`（`effectiveTemplates` / `buildTemplateWithAddedItem`）。
    画面・サーバの双方がこの純関数を使い、組み立てを二重に実装しない。
  - 入力方法は `check`（良否）/ `number`（数値・単位付き）/ `text` / `choice`（選択肢から1つ）/ `time`（時刻）。
    **数値は利用者が入力する**。項目ごとに `required`（必須）を持ち、無い旧版は「数値だけ必須」と読む（`isItemRequired`）。
    点検表は従来どおり数値の未入力を許さず、良否項目とは別に「未入力」件数に数える。
  - 航海日誌は `templateKey` = 記録種別（departure / arrival / position / remark）とし、
    入力値は `extraValues` に保持する（値の検査は `collectTemplateValues`。任意の空欄は載せない）。点検は `checklist_result.items` に同じ形で保持する。
  - 追加の権限は `manage_record_templates`（船長のみ）。陸上は `/shore/templates` から配信する。
  - **航海日誌の項目は記録の入力画面の中で直す**（利用者の依頼 2026-10-14「もっと直感的かつ自由に」）。船長には入力画面に

    過去の記録は残る。種類の名前の表示は `src/lib/voyage-log.ts` の `voyageLogLabel` 1つ（船内・陸上で共用）。

## 当直・シフトの仕様（04）

- **当直は本人の分だけ**を表示する（本日の当直・今週の当直・変更通知・メニューのバッジ）。
  全員の当直表は船長（`view_all_crew`）のみで、他船員の当直を読む処理は
  `_components/crew-watch-table.tsx` に閉じる（本番は API の権限ガードと RLS）。
- **通常配置表は船内全員**を表示する。非常配置・出入港配置は互いの持ち場を知る必要があるため、
  当直と違って全員分を出す（自分の行は「（あなた）」と明示し、先に「あなたの持ち場」を大きく置く）。
- **陸上の変更は即座に反映**する。`/api/v1/sync/stream`（SSE）が「版が変わった」ことだけを通知し、
  取り込みは従来の Pull（カーソル方式）に任せる（`useLiveSync`）。
  - 通知が届かない環境でも 60 秒の定期同期で同じ結果になる（オフライン耐性・冪等性を崩さない）。
  - 擬似オフライン中は接続しない。本番は Supabase Realtime に置き換える。
  - 版の監視には `getStoreVersion()` を使う（`getSyncStats()` は競合件数の算出で全件走査するため
    常時ポーリングに使わない）。
- 陸上は当直（`publishShiftChange`）に加えて**配置表も変更・配信できる**（`publishStationChange`）。
  どちらも追記のみで、旧レコードを `supersedesId` で置き換える（陸上正本・計画/実績分離）。
- 表示の言い換えは `src/lib/shift-plain.ts` に集約する（画面に文言ロジックを散らさない）。
  「いま◯◯当直中です／終わりまで あと◯分」「まだ打刻がありません」など、当直中・開始前・
  終了済み・予定なしの4状態を日常語で示す。

## 同期状態（V-09）

- **仕組みの言葉を出さない**（レビュー SYNC-02/03）。「イベント・キュー・カーソル・IndexedDB・隔離」ではなく
  「送っていない記録 ◯件／すべて送りました／通信なし」の帯1本と「いま同期する」のボタンで伝える。
  確認が必要な記録（競合）・取り込めなかった記録（隔離）・前回の失敗は**あるときだけ**札で出し、理由はホバー。
  擬似オフラインは「通信を切って試す」。

  `applyRuleOverrides` で閾値が上書きされ、判定結果の `appliedRuleVersion` に協定版が載る（6.5）。
- **承認は2段**: 船内（船長）と陸上（労務管理責任者）。役割優先（労務管理責任者 > 船長）は
  `resolveApproval` が解決し、船内の記録簿には「誰が承認したか」を文言で出す。
  陸上が差戻した日は船長の承認が効かないので、V-04 では承認ボタンを止めて「陸上が差戻し中」と出す。
- **警告のある打刻は「修正案つきの差戻し」で直してもらう**（レビュー LABOR-06。利用者の判断）。
  要件定義書 3.2.1「承認者も修正不可、修正は本人への差戻しのみ」を守るため、**陸上は打刻を書かない**。
  `/shore/labor/adjust` で正しい時刻・作業と理由を入れて送ると、`approval`（remanded）に `proposal`
  （change = 対象の打刻を直す / add = 押し忘れを足す）が付いて船内へ届く。本人は V-02 の「陸上からの修正の依頼」
  （履歴タブに件数）で「この内容で直す」を押し、**本人名義**の resubmit / after として入る（`proposalId` 付き）。
  反映済みかの判定は `src/lib/labor-proposals.ts`（船内・陸上で共用）。送信は使い捨ての札（opToken）から ID を
  決めるので二度押しでも二重にならない。休息への付け替え・前後1日を超える移動・未来の時刻は案にできない
  （`server/labor-proposal-service.ts`）。送った事実は監査ログに残る。
  経緯: 先に「陸上が追記型で直接訂正」を実装したが、law-checker が要件定義書・基本設計書 11.2 違反（記録簿の
  虚偽記載リスク）、sync-reviewer が打刻の書き手が2人になることによる競合を指摘し、この形に変えた。
- 陸上からの配信（シフト・配置・記録項目・お知らせ・承認）はすべて追記型イベントで、
  船内と同じ同期経路（Push/Pull・冪等キー）に積む。専用の書き込み経路を作らない。

## お知らせ（船内 `/vessel`）

- **速報とお知らせだけ**を並べる（レビュー NEWS-01）。機能の入口は横タブにあるので、
  機能メニューや「あなたへの通知」は置かない。
- 一覧は題名と日時だけ。押すと `/vessel/notices/[id]` で本文を読み、**開いた時点で既読**になる
  （NEWS-02/03。「確認しました」の一括操作は無い）。既読は端末内 meta の `noticeReadIds`
  （`markNoticeRead`）。未読は点で示す。
- `notice` は陸上正本（`origin: "shore"`）の追記型エンティティ。区分は `urgent`（速報）と
  `info`（お知らせ）で、取り消し・訂正は `supersedesId` 付きの新しいお知らせで表す。
  陸上の配信画面は `/shore/notices`。船内からは配信できない。
- 選別は `src/lib/notices.ts`（`effectiveNotices` / `unreadNotices`）に集約し、
  船内画面と陸上サービスの双方が同じ純関数を使う（期限切れ・取り消しの判定を二重に書かない）。

## 性能上の約束事

- 体感の確認は必ず `npm run preview`（本番ビルド）で行う。開発モードは画面ごとに
  コンパイルが走り未圧縮 JS を配信するため、遅さの原因を取り違えやすい。
- **Service Worker はつながっているときは必ず最新を返す**（public/sw.js）。キャッシュ優先にしてよいのは
  **名前にハッシュが入ったビルド成果物だけ**（判定は isImmutableAsset に閉じる）。開発サーバの JS は
  app/layout.js のように毎回同じ名前なので、これをキャッシュ優先にすると**直したのに何日も前の画面が
  出続ける**（実際に起きた）。版は登録先 /sw.js?v=<ビルドID> から取り、ビルドのたびに古いキャッシュを捨てる。
  **開発サーバでは登録しないだけでなく、既にある登録とキャッシュを消す**（一度入った Service Worker は
  npm run dev に切り替えても同じ localhost を握り続けるため）。
- **開発と本番の出力先は分けてある**（`next.config.mjs` の `distDir`。開発は `.next-dev`）。
  同じ `.next` に両方が書くと新旧の成果物が混ざり、サーバの HTML と手元の JS が食い違って
  **ハイドレーション不一致**になる（実際に発生した）。分けてあるので `npm run dev` を
  動かしたまま `npm run build` しても壊れない。
- 同期の受信適用は**バッチで1トランザクション**にまとめる（`applyPulledEvents`）。
  1件ずつ書くと IndexedDB の往復と useLiveQuery の再描画がイベント数だけ発生する。
  適用対象が0件のときは書き込みトランザクションを開かない（利用者の打刻を待たせない）。
- 記録直後の同期はデバウンス（800ms）でまとめる。記録はローカル確定済みなので遅延しても失われない。
- ヘッダの同期バッジは1つの `useLiveQuery` にまとめる（全画面に出るため購読数を増やさない）。
- **先読みは本番でだけ「狙いを定めたとき」に絞る**。陸上のサイドバー（`NavLink`）は
  本番ビルドでは `prefetch={false}` にし、ポインタを載せた・focus した時点で1本だけ
  `router.prefetch` する。陸上は毎回サーバで組み立てる（`force-dynamic`）ため、
  既定のままだと**画面を開くたびにサイドバーの 20 本ぶんのサーバ描画と同時接続**が走り、
  押したい画面の取得がその後ろに並ぶ（実測で最初の遷移が 3 秒）。
  船内は静的な画面なので `useRoutePrefetch` でまとめて先読みしてよい（150ms ずつずらす）。
  **開発サーバでは逆に自動先読みを残す**（`NODE_ENV === "development"` で分岐）。
  `next dev` は画面ごとにその場でコンパイルするため、先読みがそのまま
  **コンパイルの前倒し**になる。切ってしまうと押すたびに冷たいコンパイルを待つことになり、
  実測で開発サーバの遷移が 2.4〜9.0秒に悪化した（戻して 1.9〜3.3秒）。
- **和文フォントは初期表示の経路に載せない**。`@fontsource` の既定は和文を
  `unicode-range` で 124 個に割っていて、1画面で 40 前後のファイルを取りにいく
  （実測 842KB / 40 リクエスト）。割っていない `japanese-400` / `japanese-700` を
  `scripts/copy-fonts.mjs` が `public/fonts/` に用意し、`src/ui/font-loader.tsx` が
  **画面が動き出してから**読み込む（6 リクエストで全字形が揃い、以後の画面で追加取得なし）。
  それまでは端末の和文書体で表示される（`font-display: swap`）ので読めない時間は無い。
  太さは 400 と 700 だけ（和文は1太さ約 1MB。500/600 はブラウザが近い実体を選ぶ）。
- `(vessel)/vessel/loading.tsx` で遷移中の骨組みを出す。準備待ちで前の画面が固まったように
  見えるのを防ぐ（本番ではほぼ表示されない）。
- 実測値（本番ビルド・キャッシュなし・2026-09-12。測り直しは `node e2e/perf.mjs`）:
  - **初回表示**（読み込み完了まで）船内 311〜322ms / 陸上 456〜708ms
  - **押してから中身が出るまで** 船内 97〜241ms / 陸上 91〜826ms（最長は S-05 配乗計画）
  - アプリの行き来（船内 ⇄ 陸上）120〜154ms。初回同期の適用（208件）0.43s
  - 目安は**遷移1秒以内・初回表示0.8秒以内**。超えたら `e2e/perf.mjs` で原因を切り分ける
    （これまでの原因は順に「`@/ui` に HeroUI を並べていた」「サイドバー 20 本の自動先読み」
    「和文フォントの 40 分割」で、いずれも転送量ではなく**同時接続の奪い合い**だった）
- 開発サーバ（`npm run dev`）の遅さは**オンデマンドコンパイル**が原因で、実装の問題ではない。
  初回の画面表示 5〜6s・未コンパイル画面への初回遷移 1.7〜3.5s。先読みで体感は隠せるが、
  **体感の確認は必ず `npm run preview`** で行う。
  - Turbopack（`next dev --turbopack`）も計測したが、この規模では改善しなかったため採用しない
    （初回コンパイル 17.5s / 再起動後 6.2s に対し、webpack は 5.2s）。
