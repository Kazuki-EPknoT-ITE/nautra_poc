# Nautra PoC — 開発規約（基本設計書 13.2 の PoC 適用版）

このアプリは `projects/docs/` の要件定義書・基本設計書 Ver1.2 を正本とする PoC。

スコープ: **要件定義書の全業務領域（9本）を実装済み**。
船内画面 V-01〜V-10（打刻・履歴・本日の集計・船内承認・航海日誌・点検/保守・
作業/待機/燃料/引継・シフト/配置表・同期状態・相談/アンケート）＋ 事故報告、
陸上画面 S-01〜S-15（後述「陸上アプリ」節）。
デザインは `projects/docs/DESIGN.md` が正本（モノクローム・後述の「デザイン」節）。

**要件との対応を見失わないこと**: 画面・判定を足すときは、要件定義書の該当節番号を
コメントに書く。逆に節番号の無い機能は、なぜ要るのかを説明できるようにする。

## コマンド

- `npm run dev` — 開発サーバ（http://localhost:3100）。オンデマンドコンパイルのため遅い
- `npm run preview` — 本番ビルドで起動。**デモ・体感確認はこちら**
- `npm run test` — Vitest（ドメイン・同期のテーブル駆動テスト）
- `npm run typecheck` — tsc --noEmit
- `npm run build` — 本番ビルド

## ガードレール（違反コードを書かない・見つけたら直す）

1. `(vessel)` 配下で Server Components のデータ取得禁止（オフライン破壊防止）
2. 一次記録（timeRecords / records / サーバ events）への UPDATE/DELETE 禁止。訂正は差戻し→
   `supersedesId` 付き新規レコード（航海日誌・シフト計画も同じ規則。`latestBySupersedes`）
3. 法令閾値（14h/72h/休息10h 等）・安全基準（アルコール 0.15mg/L）をドメイン関数や画面内の
   定数として持つこと禁止。`src/rules/` から引数注入し、判定結果に適用版を記録する
4. 導出値（年齢・配乗可否・集計値）を入力カラムとして保持しない
5. HeroUI の直接 import は `src/ui/` 配下のみ。画面は `@/ui` 経由で使用
6. 製品名は `src/i18n/ja.ts` の `PRODUCT_NAME` からのみ参照（ハードコード禁止）
7. `(vessel)` ⇔ `(shore)` の相互 import 禁止（共有は src/domain・src/ui 等経由）
8. 同期イベントは冪等キー必須。未知種別は破棄せず隔離（quarantine）し、**アプリ更新後の
   同期で再処理**する（`reprocessLocalQuarantine`。旧版の端末が先に受信した配信が欠けたまま
   にならないようにする）。**判別ユニオンはレジストリから生成**しているので手で足す必要はない
9. **新しい記録種別の追加はスキーマを定義して `SYNC_ENTITY_REGISTRY` に登録するだけ**で
   完了させる（船内記録は `records.ts`、マスタ・事務は `masters.ts`）。種別ごとに
   Push/Pull・Dexie テーブル・適用処理を個別実装しない（汎用 `records` テーブル + `appendRecord`）
10. シフト・配乗計画・マスタは陸上正本（船内は参照のみ）。船内の実績は打刻等の別レコードで
    保持し、計画を実績で上書きしない
11. **`<p>` の中に `Chip`（`StatusChip`）や `div` を置かない**。HeroUI の Chip は `div` を描くため、
    ブラウザが `<p>` を勝手に閉じてハイドレーションが必ず壊れる（React error #418）。
    判定バッジを並べる行は `<div className="flex …">` にする
12. **`"use server"` のファイルから非 async の値を export しない**（定数・型・初期状態も含む）。
    Next.js が Server Action として扱おうとして実行時に 500 になる。定数はクライアント側に置く
13. **要配慮個人情報（既往歴・服薬）を参照したら監査ログを残す**（10.3 / 12.6）。
    `writeAuditLog({ action: "view_sensitive", … })`。ログに値そのものを載せない
14. **マスタの更新経路は1画面だけ**（12.3）。船員マスタは `/shore/crew/[id]/edit` のみが更新し、
    一覧・カルテ・届出からは書き換えない

## デザイン（`projects/docs/DESIGN.md` が正本）

「霜面の紙に引いた設計図」。**白の紙面・柔らかいグレーの面・ヘアラインの枠線**だけで階層を
作り、**色相で意味を作らない**。装飾のための色・グラデーション・ぼかしは使わない。

### トークンの置き場所（画面に直書きしない）

- 配色・角丸・型階層: `tailwind.config.ts`（HeroUI テーマ）。画面が使う
  `text-foreground-500` / `text-danger` / `bg-default-100` / `bg-primary` などの意味クラスは
  **すべてここ経由**なので、トークンを変えれば全画面に効く。
- 材質クラス: `src/app/globals.css`（`.ui-card` / `.ui-row` / `.ui-inset` / `.ui-bar` /
  `.ui-sidebar` / `.ui-modal`）。**画面は独自の影・角丸・背景色を作らない**（基本設計書 6.3）。
- 面の部品: `src/ui/`（`SurfaceCard` / `SurfaceRow` / `StatBlock` / `StatusChip` / `useModalProps`）。

### 面（三段で層を作る）

| 面 | 色 | 使いどころ |
|---|---|---|
| Canvas | `#f5f5f5` | ページ背景。いちばん広い層 |
| Surface Alt | `#fafafa` | サイドバー（`.ui-sidebar`）・控えめなカード（`.ui-row`） |
| Paper | `#ffffff` | カード（`.ui-card`）・ヘッダ（`.ui-bar`）・モーダル |

**枠線を増やさずに層を作る**のが三段の役目。面の上に面を重ねるときは必ず一段ずつ明度を変える。
カードは 1px のヘアライン + ごく浅い影の**両方**を持つ（影だけでは縁が決まらない）。

### 角丸は2値だけ

**操作要素 18px / 容器 24px**。入れ子の小ブロックだけ 10px（`.ui-inset`）。
角のある要素を作らない。HeroUI の `radius="sm"` も 18px に寄せてあるので、
画面側が size を書き分けても丸みは失われない。

### 文字

Geist（`geist` パッケージ。フォント実体を同梱するのでビルド時に通信しない）。
和文は端末のゴシックに落ちる。**型階層は Tailwind の刻みに割り当て済み**なので、
画面は `text-2xl` と書くだけで意図した行間・字間になる（`tracking-*` を個別に足さない）。

| クラス | 役割 | 大きさ / 行間 / 字間 |
|---|---|---|
| `text-xs` | caption | 12 / 1.33 / +0.6px |
| `text-sm` | body | 14 / 1.43 |
| `text-base` | body-lg | 16 / 1.5 |
| `text-lg` | subheading | 18 / 1.56 |
| `text-xl` | heading-sm | 24 / 1.33 / −0.6px |
| `text-2xl` | heading | 30 / 1.2 / −0.75px |
| `text-3xl` | heading-lg | 36 / 1.11 / −0.9px |
| `text-4xl` | display | 48 / 1.1 / −2.4px |

**船内アプリは同じ階層を1段上げる**（`.vessel .text-sm` = 16px / `.text-xs` = 14px）。
要件定義書 10.2「船員の約半数が50歳以上。大きな文字」への対応で、
新しいサイズを作らずに DESIGN.md の刻みの中で上げているため型の階層は崩れない。

### 色（ここが唯一の判断が要る所）

DESIGN.md は有彩色を `#e7000b`（Ember＝エラー）だけに限る。
一方 要件定義書 3.2.5 は「2段階アラート: 上限接近＝**注意（黄）**/ 超過＝**警告（赤）**」を
求める。法令の状態表示は装飾ではないので、**次の最小限だけを例外**として通す:

- **警告(violation) → `#e7000b`** … エラー状態そのもの。DESIGN.md からの逸脱ではない
- **注意(caution) → `#a16207`（琥珀）** … DESIGN.md への**唯一の追加色**
- **適合(ok) → 無彩色** … 従来の緑をやめた。色が付くのは「見なければならないとき」だけにする

派生する決まり:

- **0 件のときは色を付けない**（「期限が過ぎた 0」を赤で出さない）。常に赤い数字が並ぶと、
  本当に赤くなったときに気づけない。
- **速報（`notice.level === "urgent"`）は琥珀**にする。赤は法令違反のために空けておく。
- **色だけに依存しない**。記号（✓ / ⚠ / ✕）と文言を必ず併記する
  （色覚特性・直射日光下・白黒印刷でも読めるように）。
- 副次テキストは `text-foreground-500/600`（どちらも `#737373`）。
  **これより淡い文字を作らない**（`foreground-400` も同じ値に丸めてある）。

### ボタン

**見た目は役割で1種類に決める**。同じ役割のボタンを画面ごとに塗り/枠線で描き分けない。

- 主操作（送信・保存・機能への入口）: `color="primary"`（黒塗り・ピル）。
  メニューのカード内ボタンはすべてこれで、同じ高さ・同じ開始位置に揃える
- 補助操作（キャンセル・絞り込み・確認済みにする）: `variant="bordered"`（ヘアラインの輪郭）
- 記録の入口（画面内で記録を始めるタイル）: すべて `RecordTile`（同じ高さ）
- 破壊的操作: `color="danger"`

**ボタン文言は行先の名前**にし、カード幅で折り返さない長さ（目安9文字）にする。
メニューのボタン名と `GroupHeader` のタブ名・画面の副題は同じ言葉に揃える。

### レイアウト

- ページ幅は `max-w-page`（1280px）。カードの内側は 20px（`p-4`〜`p-5`）
- **陸上はサイドバー**（`.ui-sidebar`）。画面が18本あるので意味のまとまりで5群に分け、
  現在地は**色ではなく明度の反転**（黒塗り）＋ `aria-current` で示す。
  狭い画面ではヘッダ内の横並びに畳む
- **船内はヘッダのみ**。共用端末で横幅を記録に使うため、サイドバーを置かない
- カードは「タイトル＋操作ボタン」のみとし、説明文を置かない（入口・機能メニュー）。
  **通知をカードの中に置かない**（見出しと幅を奪い合ってタイトルが折れる）。通知は
  メニュー右側の「お知らせ欄」（`_components/notice-panel.tsx`）に集約する
- **一覧を全件出さない**。既定は直近ぶんだけにし、「もっと見る」で広げる
  （打刻は1日4件たまるため、全期間を出すと画面が数千ピクセルになる）。
  長さは `scratchpad/measure.mjs` で測れる

### やらないこと（DESIGN.md の Don't）

- `#e7000b` と上記の琥珀以外の有彩色を持ち込まない
- 18px / 24px 以外の角丸を作らない
- カードのヘアラインを省かない（影だけでは縁が決まらない）
- グラデーション・色の付いた影・ぼかし（`backdrop-filter`）を使わない
- 本文を 14px 未満、または `#737373` より淡くしない
- 字間を +0.05em より広く、−0.05em より狭くしない

## テスト方針

- 法令判定の変更はテーブル駆動テストの更新とセット（テスト名に条文・数値を使う）
- 同期ロジックの変更は冪等・再送・隔離のテスト追加とセット
- **法定帳票（要件定義書 9章）を足したら生成経路を持たせる**。種別を enum に足しただけで
  作れない帳票が残らないよう、`server/__tests__/statutory-documents.test.ts` が見張っている
- レビューは `.claude/agents/` の **law-checker** / **sync-reviewer** サブエージェントを使用
- E2E は `scratchpad/` の `e2e-check.mjs`（全画面のエラー）/ `e2e-flow.mjs`（主要フロー）/
  `e2e-documents.mjs`（法定帳票の生成）/ `measure.mjs`（画面の長さ・横スクロール）

## PoC の簡略化（本番との差分）

- DB: Supabase PostgreSQL → JSON ファイル（`.data/store.json`）＋ IndexedDB
  - デモデータ版（`SEED_VERSION`）が上がるとストアを作り直す（旧ファイルは退避）。
    船内端末は Pull 応答の `storeId` 変化を検知してレプリカを取り直す。旧レプリカは削除せず
    `replicaArchive` に退避し、未送信 outbox は保持する（一次記録を失わない）
- 競合ポリシーの適用: レジストリの `origin=shore`（シフト計画）を船内端末から Push した場合は
  サーバで隔離（`checkOriginPolicy`）。supersedes の分岐は `findSupersedeConflicts` で双方保持のまま
  「競合（要確認）」として V-09 / S-01 に件数表示（自動解決しない）
- 端末側の未知種別は `quarantine` テーブルへローカル隔離（破棄しない）。同期クライアントの
  IndexedDB 単体テスト・fast-check プロパティテストは未実装（要 fake-indexeddb 導入）
- 認証: 船内は PIN + 生体（WebAuthn）、陸上は担当者を選ぶ簡易サインイン。
  **権限判定の経路は本番と同じ**（`domain/authz/`）だが、RLS・テナント分離・MFA は未実装
  （デモ用固定テナント）。PIN はデモ値を平文で持つ。IC カード認証は本番で追加する
- 帳票は **HTML の印刷ビュー**（`@media print`）で、ブラウザ印刷から PDF 化する想定。
  本番は Cloud Run Jobs でサーバ生成し、電子保管する。Excel マクロ様式の取込は
  **CSV 経由**（外部ライブラリを増やさないため。xlsx 直読みは本番で対応）
- 外部連携は未接続。AIS/GPS はストアから読む**アダプタ**（`position-service.ts` の
  `fetchPositions()`）に閉じてあり、商用 API はここを差し替えるだけで載る。
  電子届出（登録届出）・e-Gov も同様に生成物までを用意し、送信経路は未接続
- 給与は打刻から時間外を算出するが、**確定時の値を保存する**（後から再計算されては困るため。
  導出値を持たない原則の意図的な例外で、その旨をコードに明記してある）
- チェックリストテンプレートは定数（本番はテナント定義・版管理テーブル）
- 同期クライアントの IndexedDB 単体テスト・fast-check プロパティテストは未実装
  （要 fake-indexeddb 導入）
- 通知のプッシュ配信（Web Push）は未実装。船内は SSE + 定期同期で受け取る

## 認証とロール（船内アプリ）

- 船内はサインイン必須。共用端末のため「船員を顔写真リストから選択 + PIN」方式とし、
  セッションは端末内（IndexedDB meta）にのみ保持する（基本設計書 11.3。通信断でも成立）。
  実装は `src/lib/vessel-session.ts` と `/vessel/login`、ガードは `(vessel)/vessel/layout.tsx`。
- 権限判定は `src/domain/authz/roles.ts` の表が唯一の情報源。画面に条件分岐を散らさず、
  `usePermission()` / `PermissionGate` / `ReadOnlyNote`（`_components/permission-gate.tsx`）経由で使う。
- ロールと主な差分（基本設計書 11.2 の権限マトリクスを船内画面に展開）:
  - 船長 captain: 全機能 + 日次労務の承認・差戻し + 対象船員の切替（他船員の参照）
  - 航海士 deck_officer: 航海日誌の記入。保守記録は参照のみ
  - 機関長 chief_engineer: 日常点検・保守の記入。航海日誌は参照のみ
  - 甲板部員 deck_rating: 打刻・点検・作業記録。日誌/保守は参照のみ、承認は不可
- 記録の作成者（recordedBy / crewMemberId）はサインイン中の本人。対象船員の切替は船長のみで、
  他ロールは常に本人固定（`useActiveCrew()`）。
- PoC の簡略化: PIN はデモ値をマスタに平文で保持し、ログイン画面に表示している。本番は
  Supabase Auth（+ 管理者ロールは MFA）と端末登録（sync_devices）を併用し、PIN はハッシュ化する。

## 打刻の仕様（01 労働時間・打刻）

- **打刻できるのはサインイン中の本人のみ**（共用端末でも記録者を取り違えない。11.3）。
  対象船員の切替は打刻には効かない（船長も自分名義でしか打刻できない）。
- 作業種別は**割り当てられた当直シフトから導出**する（`src/lib/assigned-work.ts` の
  `assignedWorkFor`。対応表 `SHIFT_TO_WORK` は打刻画面とシフト画面で共用）。
  臨時作業は「割り当て外」から打刻でき、計画との差異は 04 の計画/実績対比で確認する。
- 操作は**2段階**（作業タイルをタップ → 「作業開始」/「作業終了」を押す）。誤操作防止（6.3）。
- **並列打刻**に対応する。`buildIntervals` は作業種別ごとに開始/終了を対応づけ、
  複数の進行中区間を返す。したがって**労働時間の合計は区間の和集合**（`mergeRanges`）で
  求める（同時刻を二重に数えない）。種別別の内訳は重複を含むため合計を超えうる。
- 履歴・事後入力・差戻し再入力は打刻画面に統合（`/vessel/history` は転送のみ）。
  時刻は秒まで表示する（`fmtTimeSec` / `fmtDateTimeSec` / `fmtElapsedClock`）。
- 進行中のまま 12 時間を超えた作業には終了打刻忘れの注意を出す（並列打刻では開きっぱなしが
  溜まりやすく、進行中区間は現在時刻まで労働として集計されるため過大計上になる）。
- 権限: `punch`（本人の打刻）/ `punch_after_entry`（本人の事後入力・差戻し再入力）は全ロール、
  `adjust_crew_punch`（他船員の打刻を参照し差戻しで調整）は船長のみ。直接修正は誰もできない。

## 労務管理記録簿の仕様（02）

- 表示は役割で分ける（11.2）。一般の船員は**自分の記録だけ**、船長（view_all_crew）のみ
  表示船員の切替と乗組員一覧が出る。他船員の記録を読むコードは船長向けコンポーネントに閉じる
  （本番では API の権限ガードと RLS でサーバから返さない）。
- 承認・差戻しは船長のみ（approve_labor）。**承認者はサインイン中の本人**を記録する
  （固定の船長 ID を使わない）。承認者は打刻を直接修正できず、差戻しで本人に再入力させる。
- 権限のないサブ画面はタブごと出さない（GroupHeader の tabs に permission を付ける）。
  権限外の画面には他船員の氏名も出さない（見出しに承認者名を書かない）。
- 判定の言い換えは `src/lib/labor-plain.ts` に集約する（画面に文言ロジックを散らさない）。
  法令用語ではなく「働いた時間 / 休んだ時間 / 休みが分かれた回数」等の日常語＋
  「あと◯◯働けます」「◯◯不足する見込みです」の一文で示す。判定自体は domain が行う。

## 航海日誌の仕様（03）／点検の統合先（05）

- **03 は航海日誌だけ**にした。点検は 05「船内保守・作業記録」へ移設し、機器の日常点検・保守と
  同じ画面（`/vessel/maintenance` = 「点検・保守」）にまとめる（レビュー: 内容が重なるため統合）。
  - `/vessel/checklist` は転送のみのルートとして残す（既存リンク・ブックマーク対策）。
  - 点検表の入力・項目追加は `_components/checklist-section.tsx` に切り出し、置き場所を変えても
    同じ振る舞いになるようにした。履歴は点検表の結果と機器の保守記録を**1つの並び**で見せる。
  - 操練・アルコール検知は `/vessel/safety`（05 の3つ目のタブ）。点検でも保守でもない安全記録として
    独立させ、1画面1目的を保つ。
- **記録項目は配信で決まる**。点検表・航海日誌の追加項目は `record_template`（追記型・
  `origin: "both"`）として上司（船長）と陸上の双方から配信する。項目の追加は
  「項目を1つ足した新しい版」を `supersedesId` 付きで配信し、旧版は保持する
  （過去の記録は記録時点の `templateVersion` を持つため意味が変わらない）。
  - 解決は `src/lib/record-templates.ts`（`effectiveTemplates` / `buildTemplateWithAddedItem`）。
    画面・サーバの双方がこの純関数を使い、組み立てを二重に実装しない。
  - 入力方法は `check`（良否）/ `number`（数値・単位付き）/ `text`。**数値は利用者が入力する**。
    数値項目は未入力を許さず、良否項目とは別に「未入力」件数に数える。
  - 航海日誌は `templateKey` = 記録種別（departure / arrival / position / remark）とし、
    入力値は `extraValues` に保持する。点検は `checklist_result.items` に同じ形で保持する。
  - 追加の権限は `manage_record_templates`（船長のみ）。陸上は `/shore/templates` から配信する。
- **記録できるのはサインイン中の本人のみ**（打刻と同じ。共用端末で記録者を取り違えない）。
  航海日誌・点検・保守の画面から対象船員の切替（CrewPicker）は外し、`useSessionCrew()` を使う。
- 記録の入口ボタンは**種別で色を変えない**。出港・入港・定時記録・特記事項・出港前点検・
  安全パトロール・操練・アルコール検知はすべて共通の `RecordTile`（`_components/record-tile.tsx`）
  で描く。打刻の作業タイルと同じ紙面・同じ高さで、船内アプリ全体の操作感を揃える。

## 当直・シフトの仕様（04）

- **当直は本人の分だけ**を表示する（本日の当直・今週の当直・変更通知・メニューのバッジ）。
  全員の当直表は船長（`view_all_crew`）のみで、他船員の当直を読む処理は
  `_components/crew-watch-table.tsx` に閉じる（本番は API の権限ガードと RLS）。
- **通常配置表は船内全員**を表示する。非常配置・出入港配置は互いの持ち場を知る必要があるため、
  当直と違って全員分を出す（自分の行は「（あなた）」と明示し、先に「あなたの持ち場」を大きく置く）。
- **陸上の変更は即座に反映**する。`/api/v1/sync/stream`（SSE）が「版が変わった」ことだけを通知し、
  取り込みは従来の Pull（カーソル方式）に任せる（`useLiveSync`）。
  - 通知が届かない環境でも 60 秒の定期同期で同じ結果になる（オフライン耐性・冪等性を崩さない）。
  - 擬似オフライン中は接続しない。本番は Supabase Realtime に置き換える。
  - 版の監視には `getStoreVersion()` を使う（`getSyncStats()` は競合件数の算出で全件走査するため
    常時ポーリングに使わない）。
- 陸上は当直（`publishShiftChange`）に加えて**配置表も変更・配信できる**（`publishStationChange`）。
  どちらも追記のみで、旧レコードを `supersedesId` で置き換える（陸上正本・計画/実績分離）。
- 表示の言い換えは `src/lib/shift-plain.ts` に集約する（画面に文言ロジックを散らさない）。
  「いま◯◯当直中です／終わりまで あと◯分」「まだ打刻がありません」など、当直中・開始前・
  終了済み・予定なしの4状態を日常語で示す。

## メニューのお知らせ欄（全体）

- 右側に2つ置く。**速報・お知らせ**（陸上が配信する `notice`）と**あなたへの通知**
  （端末内のデータから導く「対応が要るもの」: 当直変更・機器の不良・未送信・承認まち）。
- `notice` は陸上正本（`origin: "shore"`）の追記型エンティティ。区分は `urgent`（速報）と
  `info`（お知らせ）で、取り消し・訂正は `supersedesId` 付きの新しいお知らせで表す。
  陸上の配信画面は `/shore/notices`。船内からは配信できない。
- 選別は `src/lib/notices.ts`（`effectiveNotices` / `unreadNotices`）に集約し、
  船内画面と陸上サービスの双方が同じ純関数を使う（期限切れ・取り消しの判定を二重に書かない）。
- 「あなたへの通知」の件数は各画面と同じ導出関数（`openMaintenanceIssues` など）を使う。
  ここで別計算しない。当直の変更は本人の分だけ数える（04 の方針と揃える）。

## 性能上の約束事

- 体感の確認は必ず `npm run preview`（本番ビルド）で行う。開発モードは画面ごとに
  コンパイルが走り未圧縮 JS を配信するため、遅さの原因を取り違えやすい。
- 同期の受信適用は**バッチで1トランザクション**にまとめる（`applyPulledEvents`）。
  1件ずつ書くと IndexedDB の往復と useLiveQuery の再描画がイベント数だけ発生する。
  適用対象が0件のときは書き込みトランザクションを開かない（利用者の打刻を待たせない）。
- 記録直後の同期はデバウンス（800ms）でまとめる。記録はローカル確定済みなので遅延しても失われない。
- ヘッダの同期バッジは1つの `useLiveQuery` にまとめる（全画面に出るため購読数を増やさない）。
- **次に開く画面は先読みする**（`useRoutePrefetch`）。メニューを見ている間に各画面を用意し、
  押してから用意を始めない。150ms ずつずらして要求し、同時に走らせない。
  開発サーバでは先読みがそのまま画面のコンパイルを進めるため効果が大きい。
- `(vessel)/vessel/loading.tsx` で遷移中の骨組みを出す。準備待ちで前の画面が固まったように
  見えるのを防ぐ（本番ではほぼ表示されない）。
- 実測値（本番ビルド・同一環境）: 起動 0.5s / 画面表示 0.2〜0.5s / **画面遷移 28〜205ms** /
  初回同期の適用（208件）0.43s / 打刻クリック→画面反映 55ms。
- 開発サーバ（`npm run dev`）の遅さは**オンデマンドコンパイル**が原因で、実装の問題ではない。
  初回の画面表示 5〜6s・未コンパイル画面への初回遷移 1.7〜3.5s。先読みで体感は隠せるが、
  **体感の確認は必ず `npm run preview`** で行う。
  - Turbopack（`next dev --turbopack`）も計測したが、この規模では改善しなかったため採用しない
    （初回コンパイル 17.5s / 再起動後 6.2s に対し、webpack は 5.2s）。
