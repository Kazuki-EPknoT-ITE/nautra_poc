# 1. はじめに

## 1.1 本書の目的

本書は、業務定義書(要件定義書 Ver 3.2)に定義された国内船主向け「船員業務管理アプリケーション」の要件を実現するための基本設計を定めるものである。システム全体構成、技術スタック、データベース、画面、API、オフライン同期、帳票、セキュリティの各設計に加え、Claude Code を用いた開発を円滑に進めるためのリポジトリ設計・開発規約・品質ゲートを定義し、詳細設計および実装のインプットとする。Ver 1.1 では、技術スタック検討会(壁打ち)で確定した採用技術・クラウド構成を全編に反映した。Ver 1.2 では、製品名を Nautra(ノートラ)に確定するとともに、「要件・機能が増加しても改修コストが線形に収まる開発ベースであるか」の観点でレビューを行い、法令ルール・承認フロー・手続き・権限・同期対象という増加しやすい領域を定義駆動へ改めた。

## 1.3 開発前提(Claude Code による開発)

本システムは Claude Code を主たる実装手段として開発する。この前提は設計判断に次の形で反映している。

- スキーマ駆動・単一言語: 全レイヤを TypeScript に統一し、Zod スキーマ→OpenAPI→フロント/バック双方の型を自動生成する。型とスキーマが AI への正確なコンテキストとなり、生成コードの整合性を機械的に担保できる。

- ドメインロジックの分離: 労働時間上限(日14h/週72h)・休息時間・配乗ブロック等の法令判定を、UI・DB に依存しない純関数パッケージに隔離する。テーブル駆動テストで仕様を表現し、Claude Code がテストを仕様として参照・検証できるようにする。

- コンテキスト設計: リポジトリ直下および各パッケージに CLAUDE.md を配置し、規約・禁止事項(打刻レコードの UPDATE 禁止、クライアントからの DB 直接アクセス禁止等)・参照すべき設計書の所在を明示する(13章)。

- 検証可能性: 帳票はゴールデンファイルテスト、同期は決定的なシミュレーションテストを用意し、AI が生成した変更を CI で自動検証する。

## 1.6 製品名・ブランド表記

本システムの製品名を Nautra(ノートラ)とする。名称表記の揺れは画面・帳票・対外資料・クラウド資源名の全体に波及するため、以下のとおり固定し、実装上の参照方法もあわせて規定する。

| **表記** | **用途**                                                                                               |
|----------|--------------------------------------------------------------------------------------------------------|
| Nautra   | 正式名称。ロゴ・対外資料・画面ヘッダ・契約書・利用規約における表記                                     |
| ノートラ | 日本語カナ表記。読み仮名として用い、資料上は常に Nautra を併記する(口頭説明時の聞き取り違いを防ぐため) |
| nautra   | 小文字表記。ドメイン・リポジトリ名・パッケージスコープ(@nautra/\*)・クラウド資源名の接頭辞に用いる     |

実装・運用上の規約を以下に示す。

- 製品名は i18n リソースの単一キー(PRODUCT_NAME)からのみ参照し、コンポーネント・帳票テンプレート・メール文面へのハードコードを禁止する(13.2 ガードレール⑨)。テナント別表示名の設定、および船舶管理会社による再提供(ホワイトラベル)への拡張余地を確保するためである。

- DB テーブル名・API パス・ドメインパッケージ名には製品名を含めず、業務語彙(crew_members・time_records・/api/v1/… 等)を用いる。これにより改称・ブランド追加時の影響範囲を、リソースファイルとインフラ命名に限定できる。

- クラウド資源(Cloud Run サービス・Artifact Registry・GCS バケット・Supabase/Sentry プロジェクト)の命名は、Terraform 変数 name_prefix(既定値 nautra)に集約し、環境識別子(dev/stg/prd)を後置する。GCS バケット名はグローバル一意であるため、プロジェクト着手時に確保する。

- 実装着手前に、商標(第9類・第42類・第35類)の調査とドメイン(nautra.jp / nautra.app 等)の取得を行う。同綴りの他業種ブランドが海外に存在するため、区分を限定した調査を行い、結果を ADR-0007 に記録する。

# 2. システム全体設計

## 2.1 全体構成

本システムは、単一の Next.js アプリケーション(船内画面+陸上画面+API)を Cloud Run 上で稼働させ、データ基盤に Supabase(PostgreSQL・Auth・Storage・Realtime)を用いる SaaS 型マルチテナントシステムである。船内は通信断を前提とし、法令遵守に必要な業務(打刻・記録・船内承認)が端末内で完結する。オンライン復帰時に自前実装の同期 API を通じて陸上クラウドへ自動同期する。全コンポーネントを東京リージョンに配置し、国内データ管理要件(要件定義書 10.3)を満たす。

>
> 船内画面(Next.js / PWA・Client Component 構成)
>
> ├ 打刻 / 航海日誌 / 点検・操練 / シフト参照 / 船内(船長)承認
>
> └ Service Worker(Serwist)+ IndexedDB(一次記録・追記のみ・送信キュー)
>
> ↑↓ 差分同期(HTTPS / 再開可能・冪等 / 圧縮) ※自前実装
>
> 【陸上クラウド(すべて東京リージョン)】
>
> Cloud Run サービス: Next.js アプリ(単一デプロイ)
>
> ├ 陸上画面(Server Components 活用)
>
> ├ API ルート(REST + OpenAPI): 同期 / ドメインサービス / RBACガード
>
> └ アラートエンジン(法令遵守・着手期限・鮮度)
>
> Cloud Run Jobs(同一コンテナイメージ): 帳票生成・集計バッチ
>
> Cloud Scheduler: 期限アラート等の定時起動
>
> Supabase: PostgreSQL(RLS二重防御)/ Auth / Storage / Realtime

> 外部連携アダプタ: AIS / e-Gov・国交省システム / メール(Resend or SES)

> 監視: Sentry(個人情報マスク必須)+ Cloud Logging / Monitoring

## 2.3 単一アプリケーション構成の採用理由

船内画面と陸上画面は、別アプリに分割せず単一の Next.js アプリケーション内のルートグループ((vessel) / (shore))として実装する。理由は次のとおり。

- 運用最小の原則: デプロイ対象・監視対象が 1 サービスに収まり、「単一ホスティング・障害点最少」というスタック選定方針(3.2)と一貫する。

- コード共有: packages/domain・schemas・ui を両画面が同一プロセスで参照でき、バージョン不整合が発生しない。

- 同一イメージの使い回し: Cloud Run Jobs(帳票・バッチ)は同じコンテナイメージを別エントリポイントで起動するだけで済み、ビルドパイプラインが 1 本になる。

- 分離の担保: Service Worker のスコープは (vessel) 配下に限定し、陸上画面が誤ってオフラインキャッシュされることを防ぐ。認可はミドルウェア+RBAC ガードでルートグループ単位に強制する。

- 将来の分割判断基準: 機能増加に伴い、①本番ビルド時間が 10 分を超える、②船内画面と陸上画面でリリース頻度・停止許容度が乖離する、③船内向けと陸上向けで必要なインスタンス特性(最小インスタンス・メモリ)が乖離する、のいずれかに達した時点で apps/web の分割を検討する。判断と結果は ADR に記録する。

- 分割コストを常に低く保つため、(vessel) と (shore) の相互 import を禁止し、共有はすべて packages/ 経由とする(ESLint 独自ルールで機械検出。13.5)。この制約を維持している限り、分割はルートグループの切り出しとデプロイ設定の追加で完了する。

## 2.4 マルチテナント方針

- 1テナント=1船舶所有者(または船舶管理会社)とし、全テーブルに tenant_id を保持する。

- 権限は二重防御とする: アプリ層(API の RBAC ガード)を第一防御、PostgreSQL の RLS を最終防衛線とし、アプリケーションのバグによる越境参照を DB 層でも遮断する(5.1, 11章)。

- 船舶管理会社が複数船主を受託するケースは、テナント間の「管理委託リンク」で参照権限を明示的に付与する(Phase 2 後半)。

## 2.5 接続4類型への対応構成

要件定義書 11章(10.1)の接続可否4類型に対し、同一アプリケーションの設定切替で対応する。

| **接続類型**     | **運用構成**                                       | **同期挙動**                                                                 |
|------------------|----------------------------------------------------|------------------------------------------------------------------------------|
| ① 常時接続可     | 船内画面をオンライン同期モードで運用               | 記録の都度、準リアルタイム同期                                               |
| ② 陸船間のみ可   | 標準構成(既定)                                     | 定期(既定15分)+手動同期。瞬断時は自動リトライ                                |
| ③ 出航前後のみ可 | 船内蓄積モード                                     | 入出港時に一括同期。未同期件数を常時表示し同期忘れを防止                     |
| ④ 全て不可       | 縮退構成: 打刻+記録簿ファイル運用(要件定義書 10.5) | 船内端末でローカル集計・記録簿ファイル出力。陸上へは媒体渡し(取込機能で吸収) |

## 2.6 拡張アーキテクチャ(Phase 3 に向けて)

- プラグイン方式: 疲労予測AI・LLM問い合わせ・配船最適化は、本体 API の公開インターフェース(OpenAPI)経由でのみデータへアクセスする疎結合サービスとして追加する。本体スキーマへの直接依存を禁止する。

- Python サービスの追加: 数理最適化(OR-Tools 等)は Python が適するため、Cloud Run 上に独立コンテナとして追加する。ホスティング先を増やさずに言語拡張が可能な構成である(3.2 の決定事項)。

- 連携アダプタ: AIS(無償/商用)、e-Gov・国交省オンラインシステム、給与計算・会計は Adapter インターフェースを介して差替え可能とする(10章)。

- 判断の最終責任: AI 系プラグインの出力は提案・警告に限定し、承認・確定操作は必ず人間(労務管理責任者等)が行う設計を維持する。

## 3.3 外部サービス依存の管理方針

外部サービスを積極活用する一方、10年単位で使われる業務システムとして、依存には次の保険を掛ける。

- Supabase: 依存する固有機能を Auth・Storage・Realtime に限定し、データ本体は素の PostgreSQL として扱う。日次で論理バックアップを自社管理の GCS バケットへも退避し、国内クラウドや自前運用の PostgreSQL へ移設可能な状態を常に維持する。将来「国内事業者による運用」を求める調達要件が出た場合の受け皿とする。

- HeroUI: 画面から直接 import せず、必ず packages/ui のラッパーコンポーネントを経由する。ライブラリ差替え時の影響を packages/ui 内に閉じ込める。

- Cloud Run: 全サービスを Dockerfile ベースで構築し、コンテナごと他基盤へ持ち出せる状態を保つ。

- Sentry・メール等の SaaS: アダプタ経由で利用し、個人情報を送信しない(11章)。

## 3.4 選定にあたっての補足

- ネイティブアプリ(iOS/Android)は Phase 1〜2 では採用せず PWA とする。船内共用端末での運用・自動更新・開発リソース集中を優先する。Phase 3 のスマホ連動(パッシブ打刻・カメラ活用)で Capacitor によるラップを再評価する。

- 生体認証を打刻認証に用いる場合は WebAuthn(端末の指紋/顔認証)を利用し、生体情報そのものはサーバへ保存しない。

- CRDT 等の汎用同期ライブラリは採用しない。一次記録が追記専用であるため、要件定義書 12.5 の競合解決ポリシーを直接実装する方が単純で監査性が高い(8章)。

- 陸上画面のコールドスタート対策として、業務時間帯のみ Cloud Run の最小インスタンス数を 1 に設定する(月数百円程度の追加で応答性を確保)。

## 4.3 横断基盤コンポーネント

- アラートエンジン: ルール(法令上限・着手期限・鮮度・未同期滞留)を宣言的に登録し、判定は packages/domain の純関数へ委譲する。定時評価は Cloud Scheduler → Cloud Run Jobs で実行し、結果は alert テーブルへ永続化してダッシュボード表示とプッシュ通知の両方に用いる。

- 監査証跡: 全マスタ更新に対し変更前後値・変更者・日時・経路(陸上/船内/外部連携)を audit_logs に自動記録する(要件定義書 12.6)。要配慮個人情報は参照も access_logs に記録する。ドメインサービス層の共通デコレータとして実装し、記録漏れを構造的に防ぐ。

- 権限制御: RBAC ガードを API 層で一元化し、要配慮項目はフィールドレベルで制御する(11.2 の権限マトリクスをコード生成)。クライアントからの DB 直接アクセスを禁止しているため、この一箇所がすべての通り道となる。

# 5. データベース設計

## 5.1 設計方針

- 正本管理の実装(要件定義書 12章): アプリが正本を持つデータと外部に正本があるデータ(写し)をテーブル設計で区別する。写し系テーブルは「有効期限」に加え「最終確認日・確認方法・確認者」を必須列とする。

- 単一実体の原則: 写真付きプロフィールは専用テーブルを持たず、船員マスタ+関連テーブルの参照ビュー(DB View)として実装する。年齢・配乗可否等の導出値はカラムに保持しない。

- 追記専用(イミュータブル): 打刻・航海日誌・点検等の一次記録テーブルは UPDATE/DELETE を DB 権限とトリガで禁止し、訂正は差戻しによる新規レコードで表現する。

- スナップショット: 届出書類は生成時点のマスタ値を JSONB で複製保存し、提出後は不変とする。

- スキーマ管理: packages/db の Drizzle スキーマ定義を単一情報源とし、マイグレーションは Drizzle Kit で SQL ファイルとして生成・レビューする(手動 DDL 禁止)。RLS ポリシー・トリガも同ディレクトリの SQL でバージョン管理する。

- RLS の適用方式(二重防御): アプリからの接続は service_role を使わず、専用の制限付きロールで行う。トランザクション先頭でテナント ID・ユーザ ID をセッション変数(set_config)にセットし、RLS ポリシーがこれを参照して行レベルの分離を強制する。第一防御はアプリ層の RBAC ガード、RLS は最終防衛線である。

- ルールの版管理: 労働時間上限・休息要件・添付要件等の判定基準は、有効期間(effective_from / effective_to)を持つ rule_sets として保持し、判定結果には適用したルール版を記録する(5.3(6))。法改正・労使協定の改定後も、過去の判定を当時の基準で再現・説明できる状態を維持する。帳票における form_version(9.2)と同じ考え方を、労務判定にも適用するものである。

- 定義駆動: 承認フローの段数・手続きイベント連鎖・権限は、コード上の分岐ではなく定義テーブルで表現する(5.3(7)(8))。テナントごとの運用差異と、法令・様式追加に伴う手続きの増加を、マイグレーションなしで吸収するためである。

- 認証基盤の移設性: 業務テーブルの外部キーは自前の users.id にのみ張り、Supabase Auth の識別子(auth.uid)は users テーブルの1列として保持する。認証方式の変更や顧客からの SSO(SAML/OIDC)要求に対し、影響範囲を users テーブルに限定する(3.3 の依存管理方針の具体化)。

## 6.3 UI 設計方針(HeroUI の適用)

- UI コンポーネントは HeroUI を基盤とし、packages/ui でラップした専用コンポーネントのみを画面から使用する。HeroUI の直接 import は禁止し、ライブラリ差替え時の影響を packages/ui 内に閉じ込める(3.3)。テーマは HeroUI のテーマ機構で「船内テーマ(大文字・高コントラスト)」「陸上テーマ(情報密度優先)」の2系統を定義する。

- 文字サイズは船内画面基準 18pt 以上、打刻ボタンは片手・手袋操作を想定し高さ 64px 以上。1画面1目的とし、打刻はホームから2タップ以内で完了する。

- 誤操作防止: 打刻直後の確認トースト+直前打刻内容の常時表示、日付跨ぎ・未来日時のガード、取消は差戻しフローへ誘導。

- 色だけに依存しない表示(黄=注意/赤=警告にアイコン・文言を併記)。

- 文言・ラベルはリソースファイルに外部化し、多言語UI(外国人船員対応)へ拡張可能とする。多言語化は後付けの影響範囲が全画面・全帳票に及ぶため、Phase 1 から i18n の器のみを導入する(既定は日本語単一運用)。作業種別名・チェックリスト項目等の DB 上のマスタ名称も多言語カラム(jsonb)で保持し、製品名は PRODUCT_NAME キーとして同じ仕組みで管理する(1.6)。

- packages/ui は Storybook で見本化する。Claude Code には「packages/ui のコンポーネントのみ使用」の規約を課し、画面ごとの独自スタイルを禁止する。

# 7. API設計

## 7.1 設計方針

- Next.js Route Handler による REST + OpenAPI 3.1。リソース設計は 5章のエンティティと対応させる。スキーマは packages/schemas の Zod 定義を単一情報源とし、OpenAPI・クライアント SDK・バリデーションを自動生成する。

- データアクセスの唯一の経路: クライアント(船内・陸上画面)からの DB 直接アクセスは禁止し、すべて本 API を経由する。supabase-js のクライアント利用は Auth・Storage・Realtime に限定する(3.2 の決定事項。ESLint ルールで機械検出)。

- 認証は Supabase Auth の JWT(Bearer)。全 API でテナントコンテキストを必須とし、RBAC ガード→ドメインサービス→RLS(セッション変数)の三段で分離を担保する。

- 書き込み系 API は Idempotency-Key ヘッダを受け付け、同期・再送に対して安全とする。

- エラーは RFC 9457(Problem Details)形式で統一する。

# 8. オフライン同期設計

## 8.1 方式概要(自前実装の確定)

同期は自前実装とする。PowerSync 等の同期サービスとの比較検討の結果、①運用時の障害点が最少(同期サービス+内部ストレージの追加運用が不要)、②法定記録(打刻)の障害時に挙動を自社コードとログで完全に説明できる、③外部サービスの継続性リスクがゼロ、の3点から「運用的に最も安全な策」として決定した(3.2)。本件は一次記録が追記専用で双方向マージがほぼ発生しないため、自前実装の難易度は一般的なオフラインアプリより低い。

船内画面は全ての記録をローカル(IndexedDB)へ先に書き込み、同期イベントとして送信キューに積む(ローカルファースト)。同期は「船内→陸上の Push」と「陸上→船内の Pull(マスタ配信)」の2方向で構成し、いずれも再開可能・冪等とする。

> \[船内\] 記録入力 → IndexedDB(一次記録・追記のみ) → 送信キュー
>
> → Push /api/v1/sync/push (バッチ・gzip圧縮・チェックポイント付き)
>
> サーバ: idempotency_key で重複排除 → ドメイン処理 → ACK
>
> ← Pull /api/v1/sync/pull?since=\<version\> (マスタ/シフト/承認結果の差分)
>
> 端末: バージョンカーソルを保存し次回はその続きから

## 8.2 同期イベント仕様

| **項目**   | **内容**                                                                                      |
|------------|-----------------------------------------------------------------------------------------------|
| イベントID | ULID(端末採番)。時系列順序性を持ち再送時も不変                                                |
| 冪等キー   | device_id + イベントID。サーバは UNIQUE 制約で二重適用を防止                                  |
| ペイロード | Zod スキーマ(packages/sync-protocol)で型定義。スキーマバージョン番号を保持                    |
| バッチ     | 最大500件/リクエスト。途中失敗時は ACK 済み位置から再開(チェックポイント)                     |
| 転送量削減 | 差分のみ送信+gzip。写真等のバイナリは別キュー(帯域があるときのみ)で送信し、レコードは先行同期 |
| 時刻       | 端末時刻とサーバ受信時刻を両方保持。端末時刻の大幅乖離は警告(打刻の証跡性確保)                |

## 8.3 競合解決(要件定義書 12.5 準拠)

| **レコード種別** | **解決規則(実装)**                                                                   | **根拠**         |
|------------------|--------------------------------------------------------------------------------------|------------------|
| 打刻・一次記録   | 追記のみで競合が構造的に発生しない。同一時刻帯の重複打刻は双方保持し集計側で警告表示 | 3.2.1 改変不可   |
| 船員・船舶マスタ | 陸上優先。船内からの変更は change_requests として起票し、陸上承認後に反映            | 届出書類の入力元 |
| 承認ステータス   | 役割優先順位(労務管理責任者\>船長)。同role同時承認は後勝ち+履歴保全                  | 船員法第67条の2  |
| シフト・配乗計画 | 計画は陸上優先。船内実績は別レコードで保持し計画/実績を分離                          | 計画権限は陸上   |
| 自動解決不能     | sync_conflicts へ双方の値を保持し「要確認」として管理者へ提示。破棄しない            | データ欠落防止   |

## 8.4 同期状態の可視化・運用

- 船内・陸上の双方に「未同期件数 / 最終同期日時 / 競合件数」を常時表示する(V-09, S-01)。

- 未同期滞留(既定: 24時間超)をアラートエンジンの対象とし、同期忘れを検知する。

- 競合の発生件数・解決結果を記録し、運用改善の指標としてダッシュボードに集計する。

## 8.5 検証方法(Claude Code 開発との接続)

- packages/sync-protocol に「複数端末×切断×再送」を再現する決定的シミュレータを実装し、fast-check によるプロパティテスト(収束性・非破壊性・冪等性)を CI 必須とする。

- 同期ロジックの変更 PR は、シミュレーションテスト追加を必須とする旨を CLAUDE.md に明記する。

## 8.6 拡張性・互換性方針

同期対象の記録種別は Phase 1〜2 を通じて継続的に増加する。同期処理を種別ごとに個別実装すると、追加のたびに冪等・再開・競合解決の実装とテストが必要となり、機能追加コストが線形に増える。また船内端末は現場都合で更新が遅れるため、新旧バージョンの共存を前提とした互換性規則を実装当初から組み込む必要がある。

- エンティティレジストリ方式: packages/sync-protocol に「追記型エンティティ」を登録すると、Push/Pull・冪等キー処理・チェックポイント・競合ポリシー適用が共通実装で有効になる構成とする。新しい記録テーブルの追加は、Zod スキーマと競合ポリシー種別の登録のみで完了させ、同期処理の個別実装を不要とする。

- 競合ポリシーは 8.3 の分類(追記のみ / 陸上優先 / 役割優先 / 計画・実績分離)を列挙型として保持し、エンティティごとに宣言的に指定する。ポリシーの実装は packages/sync-protocol の純関数に集約する。

スキーマ版の共存に関する規則を以下に定める。

| **事象**                  | **規則**                                                                                                                                     |
|---------------------------|----------------------------------------------------------------------------------------------------------------------------------------------|
| 新サーバ × 旧クライアント | 旧スキーマ版のイベントを1メジャーバージョン分受理する(7.3)。受理不能な場合も破棄せず sync_quarantine へ退避する                              |
| 旧サーバ × 新クライアント | クライアントは送信前にサーバの対応スキーマ版を取得し、未対応の種別は送信キューに保持したまま待機する。端末側で記録が失われないことを優先する |
| 未知フィールド            | 破棄せず原文のまま保持し、Pull 時にもそのまま返す(往復保全)。バリデーションは既知フィールドのみを対象とする                                  |
| 未知イベント種別          | エラーとせず sync_quarantine に隔離し、サーバ更新後に再処理する。隔離件数は同期状態画面(V-09 / S-01)およびアラートの対象とする               |
| スキーマ版の廃止          | sync_devices に報告された利用版を確認し、当該版を利用する端末が存在しないことを確認したうえで廃止する                                        |

- 上記の互換性規則は Phase 1 の同期基盤実装時点で組み込む。後付けの場合、旧端末が送信した記録が受理されずに失われる可能性があり、法定記録の欠落は事後の回復が困難であるため、先行して実装する。

# 11. セキュリティ設計

## 11.1 基本方針

- 要配慮個人情報(既往歴・服薬状況・健康診断結果・相談記録)を扱う前提で、個人情報保護法に準拠した「権限細分化・暗号化・アクセスログ」を全機能共通の必須要件とする(要件定義書 10.3)。

- 通信は TLS 1.2 以上、保管は Supabase のストレージ暗号化+要配慮列のアプリケーションレベル暗号化(別鍵)。クラウド選定に依存しない防御層として維持する。

- 全コンポーネント(Cloud Run・Supabase・バックアップ退避先 GCS)を東京リージョンに配置し、データは国内で管理する。

- データアクセス経路の一元化: クライアントからの DB 直接アクセスを禁止し、全アクセスを API(RBAC ガード)経由とする。これにより権限判定・フィールドマスク・アクセスログが構造的に一箇所へ集約される(3.2, 7.1)。

## 11.3 認証設計

- 個人認証: Supabase Auth(メール+パスワード)。管理者・労務管理責任者ロールには MFA を推奨(将来必須化をテナント設定で選択可能)。

- 船内共用端末: 端末を「デバイス」として登録(sync_devices)し、端末単位の認証で同期資格を持たせる。打刻時の本人特定は「船員を顔写真リストから選択+任意で PIN」方式とし、個人の Supabase セッションに依存させない。これによりオフライン時も打刻が成立する。打刻認証の強度(なし+打刻者表示 / PIN / IC カード / 生体\[WebAuthn\])は要件どおり運用選択制とし、詳細設計で確定する。

- 紛失時対応: 端末の同期資格をリモートで失効させる。ローカルの未同期データは端末暗号化ストレージに保持。

## 11.4 監査・証跡

- audit_logs: 全マスタ更新の変更前後値・変更者・日時・経路(陸上/船内/外部連携)。外部連携による自動更新は連携元・取得日時を併記し手動更新と区別する(要件定義書 12.6)。

- access_logs: 要配慮情報は参照も記録。閲覧理由の入力を必須とする画面制御。

- 打刻等の一次記録はトリガで UPDATE/DELETE を拒否し、DB ロール権限でも同様に制限する(アプリ・DB の二重防御)。アプリ接続は service_role を使用しない(5.1)。

## 11.5 その他の対策

- Cloud Run の前段に必要に応じて Cloud Armor(WAF・DoS 対策)を配置。Supabase 側は接続元制限と Auth のレート制限を利用する。

- テレメトリの保護: Sentry へのエラー送信時は個人情報・要配慮情報を送らないマスキング設定を必須とし、規約として CLAUDE.md に明記する(送信前スクラビング+フィールド許可リスト方式)。

- 依存パッケージの脆弱性スキャン(CI)と、Claude Code 生成コードに対する秘密情報混入チェック(gitleaks)を必須とする。

- 移設可能性の担保(3.3): 日次論理バックアップの自社 GCS 退避により、Supabase 障害・契約変更時にも国内環境へデータごと移設できる状態を維持する。

# 13. Claude Code による開発方針

## 13.1 開発の基本サイクル

本プロジェクトは「仕様(ドキュメント+スキーマ+テスト)を人間が確定し、実装を Claude Code に委任し、機械検証と人間レビューで品質を担保する」サイクルを標準とする。

> ③ Claude Code へ実装委任(Plan モードで実装計画を確認 → 実装)

> ⑤ PR レビュー(人間。13.7 の必須領域は2名レビュー)
>
> ⑥ マージ → Cloud Run 検証環境へ自動デプロイ → E2E(Playwright: 業務フロー4本)

## 13.3 スキーマ駆動・テスト駆動の運用

- packages/schemas(Zod)と packages/db(Drizzle)を唯一の型定義源とし、API・フロント・同期プロトコルはすべて生成物を import する。Claude Code への指示は「スキーマを先に変更し、型エラーを解消する形で実装せよ」を定型とする。

- 法令判定(労働時間・休息・配乗ブロック・添付要件)は、要件定義書の条文・数値をそのままテストケース名に用いたテーブル駆動テストで表現する(例: 「1日の労働時間が14時間を超えると警告」「連続する任意の1週間で72時間超過を検知」「休息時間の分割回数上限」)。テストが仕様書として機能し、Claude Code の実装・リファクタの安全網となる。

- 境界値(基準労働期間の月〜年可変、安全臨時労働の別枠除外等)は人間がテストケースを確定し、実装のみ委任する。

## 13.6 ブランチ・PR 運用

- trunk-based(main + 短命 feature ブランチ)。1 PR = 1 Issue = 1機能単位とし、Claude Code のセッションも PR 単位で区切る。

- PR テンプレートに「対応する要件定義書の節番号」「テスト追加内容」「人間レビュー必須領域への該当有無」を必須項目とする。

- Claude Code GitHub Actions による PR 自動レビュー(law-checker / sync-reviewer)を第一次レビューとし、人間レビューの負荷を軽減する。

## 13.7 人間レビュー必須領域

以下は AI 生成であっても必ず人間(該当領域の担当者)が承認する。

- 法令判定ロジックと閾値(labor-law / manning / filing-rules)の変更

- 権限マトリクス・RLS ポリシー・要配慮情報の取り扱いに関する変更

- 同期の競合解決ポリシーに関わる変更

- 法定様式テンプレートのレイアウト(最終的に管轄運輸局・海事代理士等への確認を前提とする ― 要件定義書 6章 注記)

- DB マイグレーション(特に既存データの変換を伴うもの)・RLS ポリシー変更

## 13.8 ドキュメント運用

- 設計判断は docs/adr/ に ADR として記録し、CLAUDE.md から参照させる。技術スタック検討会の決定(3.2)を ADR-0001〜0006 として初期登録する。Claude Code に「関連 ADR の確認」を実装前手順として課す。

- 要件定義書の改版(Ver 3.2 以降)時は、差分を Issue 化して本設計書・スキーマ・テストへ反映する。トレーサビリティは Issue の節番号リンクで維持する。

- 本版(Ver 1.2)の決定は ADR-0007 製品名・ブランド表記 / ADR-0008 法令ルールの版管理 / ADR-0009 同期スキーマの互換性方針 / ADR-0010 権限のデータ化 として登録する。

- 要件のトレーサビリティは、節番号ではなく安定ID(REQ-\<領域\>-\<連番\>。例: REQ-LABOR-001)で維持する。要件定義書の改版で節番号が移動しても、Issue・テスト・コードからの参照が切れないようにするためである。節番号は補助表記として併記し、Issue テンプレートには安定IDの記入欄を設ける。
